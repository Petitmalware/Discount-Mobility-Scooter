# Store administration

The `/admin` route supports server-verified email/password sign-in. Set server runtime values `ADMIN_AUTH_MODE=password`, `ADMIN_LOGIN_EMAIL`, `ADMIN_PASSWORD_HASH` and `ADMIN_SESSION_SECRET`. Keep their actual values out of Git and browser bundles. Never store the plaintext password. The hash format is `pbkdf2-sha256$100000$<32 lowercase hex salt>$<64 lowercase hex derived key>`: PBKDF2-HMAC-SHA256, a cryptographically random 16-byte salt, 100,000 iterations and a 32-byte output. This count stays within the native Workers PBKDF2 operation limit; verification uses the [Workers Web Crypto API](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/). Generate `ADMIN_SESSION_SECRET` from at least 32 random bytes, encoded as hex or unpadded base64url. `.env.example` documents names and empty placeholders only.

Password mode does not trust ChatGPT identity headers or the former email allowlist. Any password configuration, including a partial configuration or unknown authentication mode, fails closed until valid secrets are present. Only installations with no password settings can use legacy ChatGPT sign-in plus an exact `ADMIN_EMAILS` allowlist; that mode requires Sites’ trusted identity injection and is not suitable for a directly exposed generic Worker.

Successful sign-in issues a signed, host-bound `__Host-dms-admin` cookie with `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, no Domain and a maximum four-hour lifetime. It cannot be shared across the custom domain and the Sites hostname: sign in separately on each host. HMAC verification rejects tampering. Rotating the password hash, login email or session secret immediately invalidates existing sessions after the new runtime configuration is deployed. Sign out clears the current browser cookie through a same-origin POST; copied stateless cookies otherwise expire within four hours or can be revoked by rotating credentials. A production HTTPS connection is required for the browser to store and send the protected cookie.

Login accepts a same-origin JSON POST at `/api/admin/login`; logout is a same-origin JSON POST at `/api/admin/logout`. Login attempts are limited durably in D1 before password derivation: five per IP and thirty across the account per fifteen-minute window. Invalid credentials receive the same generic message. Credentials and tokens are never logged. No password-reset or public account-registration endpoint is exposed.

Product edits are durable D1 overrides of the checked-in seed catalog. Add a scooter as a draft, check its specification and reference-price source, confirm image publication permission and your supply arrangements, then publish. The **Available** status is an explicit owner assertion. The seed’s **Confirm availability** status is not an inventory guarantee. Archive removes a product from browsing and new quote requests while preserving its details.

Business email and phone are optional and hidden from the storefront when blank. Prices are stored in the selected catalog currency; changing currency does not perform exchange conversion. Reprice all products before changing currency. Shipping, tax, returns and warranty terms must reflect the actual business and be confirmed in the written quote.

BTC and USDT entries are receiving-address metadata, not private keys. They are visible only to an authorized administrator and are excluded from the public catalog response. An enabled method with no address (and, for USDT, no network) falls back to a payment-assistance inquiry. Adding these settings does not create automatic payment processing. Verify the exact receiving address, USDT network, invoice amount, expiry, delivery and refund terms independently before sending a customer an invoice. Never infer payment success from a customer screenshot or transaction ID alone.

Customer requests appear in **Quote requests**. A successful request means D1 saved the contact details, product/price snapshot, preference and opaque reference. It does not confirm stock, reserve goods, submit a blockchain transaction, take a payment or send an email. Follow up using the customer’s email or phone and update status to Contacted, Quoted or Closed. Keep customer records private and apply your business’s data-retention policy. The dashboard displays the latest 200 requests.

Every mutation validates inputs on the server. Cart prices come from the server catalog, not the browser. Same-origin JSON checks and payload limits apply to writes. Inquiry submission is limited to five requests per signed-in identity (or IP for anonymous visitors) per fifteen-minute window; administrative writes are limited to 100 per signed-in administrator per window. Parameterized SQL is used throughout. Schema changes are migration-owned and are never run in an HTTP handler.

Run `npm test` (or `node --test tests/*.test.mjs`). Tests cover the password derivation against an independent implementation, session tampering/expiry/host binding/credential rotation, cookie attributes, login/logout routes, input limits, contact validation, authoritative prices, cross-origin writes and catalog integrity. HTTP auth route tests use isolated environment and rate-limit adapters; hosted QA additionally verifies the real D1 and cookie round trip.

## Photo galleries

Use8 distinct exact-model images whenever possible. Publishing requires at least 5. If only 5–7 genuine images can be sourced, enter a specific source-availability explanation in the gallery exception field. Duplicate links and CDN size/quality variants count once. Up to 16 distinct images are supported, and blank lines in pasted URL lists are ignored. Photo previews and the distinct-image counter help check a listing before saving.

## Customer reference visibility

Source URLs, reference prices, research dates and gallery exception notes stay in protected admin records. The customer API and server-rendered pages use an explicit public product projection. Customer galleries show every thumbnail in a four-column grid.

Standing and 2-wheel are available as admin categories. Standing models can record speeds up to 35 mph; seated listings retain the 25 mph validation limit. Classify standing models explicitly and describe the rider balance requirements, range conditions and optional configurations accurately.
